# 대화 맥락 유지 (계획서 §6-1 [5], §6-2)

> 측정일: 2026-09-18 / 임베딩 BGE-M3 / 재구성 claude-haiku-4-5 (claude -p) / 더미 지식베이스

## 결론

같은 사람이 여러 번에 걸쳐 말해도 맥락이 유지된다. 두 장치로 한다.

| 장치 | 역할 | 구현 |
|---|---|---|
| **질문자별 대화 기억** | 누가 무엇을 말했고 봇이 뭐라 답했는지 | `src/kakaobot/memory.py` |
| **질문 재구성** | 지시어·생략을 풀어 검색 가능한 질문으로 | `Answerer.rewrite()` |

## 왜 재구성이 필요한가 — 측정

앞선 대화 뒤에 온 후속 질문 4개로 RAG 검색 정확도를 쟀다.

| 방식 | 정답 | 문제 |
|---|---|---|
| 단독 검색 (마지막 메시지만) | 1/4 | 지시어 질문은 점수가 낮아 에스컬레이션 |
| **앞 질문과 단순 연결** | 1/4 | **앞 주제 문서로 끌려가 틀린 답을 자신 있게 함** |
| **재구성 후 검색** | **4/4** | — |

단순 연결이 가장 위험하다. "그럼 분할도 되나요?" 에 앞 질문 "수강료가 얼마인가요?" 를 붙이면
**수강료 금액 문서가 높은 점수로** 잡혀 분할 질문에 금액을 답한다. 계획서 §3 fail-closed 위반이다.

| 후속 질문 | 재구성 결과 | 점수 |
|---|---|---|
| 그럼 분할도 되나요? | 수강료를 분할해서 결제할 수 있나요? | 0.697 |
| 얼리버드도 똑같아요? | 얼리버드 상품도 동일한 환불 기한이 적용되나요? | 0.601 |
| 그거 언제까지 볼 수 있어요? | 녹화본을 언제까지 볼 수 있어요? | 0.695 |
| 빠지면 어떡해요? | 수업을 빠지면 어떡해요? | 0.611 |

## 설계 결정

### 화면 긁기 → 질문자별 기억으로 교체

처음엔 `ax-read` 로 읽은 화면 메시지에서 맥락을 뽑았다. 세 가지가 안 됐다.

| 문제 | 원인 |
|---|---|
| 봇 자신의 답변이 빠짐 | 자기 메시지 필터가 거름 |
| 화면 밖 발화가 사라짐 | `ax-read` 는 최근 20개만 줌 |
| 오래된 맥락이 안 사라짐 | 만료 개념이 없음 |

서비스가 질문자별로 직접 기록하도록 바꿨다.

### 트리거되지 않은 발화도 쌓는다

```
Mina: 저 질문이 있는데요       ← 물음표 없음, 트리거 안 됨
Mina: 환불 규정이             ← 트리거 안 됨
Mina: 얼리버드도 되나요?       ← 트리거됨. 앞 두 줄이 이 질문의 맥락
```

### 재구성 결과는 검색에만 쓴다

답변 LLM 에는 **원문 질문 + 대화 이력**을 준다. 재구성문도 사용자 입력에서 파생된 텍스트라
노출면을 줄이기 위함이다. 재구성기의 역할은 **검색 정확도를 올리는 것**뿐이다.

### 재구성이 실패하면 원문으로 검색한다

LLM 오류, 빈 응답, 200자 초과, `<` 태그 포함 → 전부 원문으로 검색한다.
원문 검색이 애매하면 점수가 낮아 에스컬레이션되므로 안전하다.

### 첫 질문엔 재구성하지 않는다

맥락이 없으면 재구성할 것도 없다. LLM 호출 1회를 아낀다.

### 봇 답변 중 에스컬레이션 문구는 기억하지 않는다

"확인 후 답변드릴게요" 는 정보가 없다. 실제로 **전송된 답변만** 기억한다.

## 설정

```toml
[context]
window_turns = 5          # 질문자별 최근 N턴 (사용자+봇 한 쌍이 1턴)
max_age_minutes = 30      # 이보다 오래된 발화는 맥락에서 뺀다
```

## 비용

맥락이 있는 질문은 LLM 을 **2회** 호출한다 (재구성 + 답변). claude-cli 기준 약 6초씩,
합계 **약 12초**. 첫 질문은 1회.

## 알려진 한계

1. **재구성이 넓어질 수 있다.** 이력에 주제가 둘 이상 섞이면 "분할 납부 및 환불 정책" 처럼
   두 주제를 합친 질문이 나온다. 더미 자료(12조각)에선 정답을 찾았지만, 실제 자료에서
   검색이 흐려질 수 있다. `audit.jsonl` 의 `search_query` 로 추적한다.
2. **재시작하면 맥락이 사라진다.** 프로세스 메모리에만 있다. 30분짜리라 수용했다.
3. **같은 이름의 다른 사람을 구분하지 못한다.** 오픈채팅 닉네임만 보이고 사용자 ID 가 없다
   (Phase 0 §5-3). 닉네임이 같으면 맥락이 섞인다.
4. **스레드 안의 대화는 아직 별도 맥락으로 다루지 않는다.** `thread.py` 가 서비스에
   연결되면 스레드가 자연스러운 맥락 경계가 된다.

## 무엇이 저장되고 무엇이 사라지는가

> 결정: 2026-09-18

**맥락(봇이 참고하는 기억)은 디스크에 저장하지 않는다.** 프로세스 메모리에만 있고
30분이 지나거나 재시작하면 사라진다.

**대화 내용은 로그로 남는다.** 보존 기간이 지나면 날짜 파일째 지운다.

| 무엇 | 어디 | 보존 |
|---|---|---|
| 대화 맥락 | 메모리 | **30분**, 재시작 시 소멸 |
| 봇이 처리한 질문·답변·근거·점수 | `logs/audit/YYYY-MM-DD.jsonl` | **30일** |
| 봇이 답하지 않은 메시지 원문 | `logs/filtered/YYYY-MM-DD.jsonl` | **7일** |
| 운영 로그 | `logs/kakaobot.log` (자정마다 분리) | **30일** |
| 에스컬레이션 질문 | 텔레그램 서버 | **텔레그램 정책** (통제 밖) |

발신자 닉네임은 **그대로 기록한다** (에스컬레이션 대응 시 누가 물었는지 알아야 하므로).

### 왜 미처리 메시지를 짧게 두는가

봇이 답하지 않은 메시지까지 무기한 쌓으면 **봇이 오픈채팅방 전체 대화 기록기**가 된다.
익명 다수가 들어오는 방이다. 이 기록의 용도는 D2(트리거 조건) 튜닝 — "답했어야 했는데
놓친 질문" 찾기 — 뿐이라 일주일이면 충분하다.

### 정리 시점

서비스가 **하루 한 번** (첫 폴링 때) 보존 기간이 지난 파일을 지운다.
서비스가 꺼져 있으면 지워지지 않으므로, 장기간 정지 후에는 기동 즉시 정리된다.

### 바꾸려면

```toml
[logging]
retention_days_audit = 30
retention_days_filtered = 7
```
