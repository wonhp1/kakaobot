# 댓글 스레드 답장 — 조사 및 구현

> 조사일: 2026-09-18 / KakaoTalk 25.9.1 / 구현: `src/kakaobot/thread.py`

## 결론

**특정 메시지에 댓글(스레드)로 답할 수 있다. 마우스를 전혀 움직이지 않는다.**

```
① 메시지의 AXCell 에 AXShowMenu    → 카카오톡 컨텍스트 메뉴
② '댓글' AXMenuItem 에 AXPick       → 스레드 창이 열림
③ 입력창 AXTextArea 에 AXValue 설정
④ '전송' AXButton 에 AXPress
```

전 구간에서 커서 좌표가 변하지 않음을 매번 측정해 확인했다.

## 조사 경과

### 처음 판단 — "물리 마우스가 필요하다" (틀림)

메시지에 마우스를 올리면 `↳ ♡` 버튼이 나타난다. 그런데:

- **실제 마우스가 그 행 위에 있을 때만** AX 트리에 나타난다
- 나타나도 **액션이 없다** (`AXPress` 불가)
- 따라서 사용자 커서를 움직여야 한다는 결론을 냈다

### 후보 경로 검토

| # | 방법 | 결과 |
|---|---|---|
| A | 메뉴 막대 | **불가** — `카카오톡`/`편집`/`창`/`도움말` 어디에도 답장·댓글 없음 |
| **B** | **다른 AX 요소의 액션** | **성공** — `AXCell` 에 `AXShowMenu` 가 있었음 |
| C | PID 지정 마우스 이벤트 | 시험 안 함 (B 로 해결) |
| D | 말풍선 바깥 우클릭 | 시험 안 함 |
| E | 키보드 단축키 | 시험 안 함 |

### 놓쳤던 것

처음엔 **행(`AXRow`)** 의 액션만 봤고 비어 있었다. 한 단계 안쪽 **셀(`AXCell`)** 에
`AXShowMenu` 가 있었다. 호버 버튼과 **같은 기능이 컨텍스트 메뉴에도 있었다.**

## ⚠️ 카카오톡의 AX 액션 목록은 믿을 수 없다

| 요소 | 목록에 표시된 액션 | 실제로 되는 것 |
|---|---|---|
| `AXRow` | 없음 | — |
| `AXCell` | `AXShowMenu` | `AXShowMenu` 동작 |
| **`댓글` 메뉴 항목** | `AXPress`, `AXPick` | **`AXPick` 만.** `AXPress` 는 **0(성공)을 반환하고 아무것도 안 함** |
| **`전송` 버튼** | **없음** | **`AXPress` 가 동작함** |

목록에 있는 게 안 되고, 목록에 없는 게 된다. **반환값을 믿지 말고 결과를 다시 읽어 검증해야 한다.**
`thread.py` 는 전송 후 스레드 메시지 목록을 다시 읽어 댓글이 실제로 붙었는지 확인한다.

## 스레드 창 구조

| 항목 | 내용 |
|---|---|
| 창 제목 | **빈 문자열** — `openkakao-cli` 의 제목 매칭으로는 찾을 수 없음 |
| 식별법 | 제목이 비어 있고 **`채팅방에 함께 보내기` 체크박스**를 가진 창 |
| 메시지 목록 | 일반 채팅창과 동일 (`AXScrollArea > AXTable > AXRow > AXCell`) |
| 발신자 추출 | 패치 003 로직이 **그대로 통한다** |
| 부속 창 | `댓글 달린 메시지` (스레드가 달린 메시지 목록) 가 함께 열림 |

## 채팅방에 함께 보내기

**켜기로 결정** (2026-09-18). 댓글이 스레드와 본방 양쪽에 올라간다.

본방에 미러링된 댓글은:
- `outgoing=True` 로 읽혀 **자기 메시지 필터가 정상적으로 거른다** (무한 루프 없음)
- 행에 `AXButton` 이 하나 더 붙는다 — 스레드에서 온 메시지를 구분하는 표식으로 쓸 수 있다.
  2026-09-26부터 실제로 쓴다: 버튼만으로는 스레드가 달린 원글('댓글 N')과 같아서, 말풍선 위
  원글 인용 칸(글 상자가 40 넘게 내려앉음)과 함께 본다 (`thread.thread_comment_rows`,
  docs/followup.md '방에도 함께 올라온 추가 질문')

| 대상 메시지 | 결과 | 커서 |
|---|---|---|
| `오늘 강의 좋았습니다` | 스레드 + 본방 도착 | 이동 없음 |
| `수강료가 얼마인가요?` (모듈 경유) | 스레드 + 본방 도착 | 이동 없음 |
| `환불은 언제까지 되나요?` (실제 파이프라인 답, `KakaoClient.reply`, 2026-09-20) | 스레드 + 본방 도착, 3.0초, `via=thread` | 이동 없음 · **맨 앞 앱 유지** |

## 구현 시 주의

1. **같은 본문이 여럿이면 가장 최근 것**을 고른다. 봇은 방금 들어온 질문에 답하므로.
2. 스레드 창은 **매번 닫는다.** 남겨두면 제목 없는 창이 여럿 생겨 식별이 모호해진다.
3. 입력창에 **작성 중인 내용이 있으면 덮어쓰지 않는다** (운영자가 쓰던 댓글 보호).
4. 열린 스레드의 **원본이 대상 메시지와 일치하는지** 확인한다 (엉뚱한 스레드 방지).

## 서비스 연결 (2026-09-20, D10)

봇은 질문 메시지에 **댓글로** 답하고 방에도 함께 올린다 (`[send] reply_mode = "thread"`,
`mirror_to_room = true`). 답을 못 할 때의 안내 문구(D11)도 같은 경로로 단다.

```
LLM 답 완성
  → 무작위 지연 (1~3초)
  → 설정 다시 읽기 — 그 사이 긴급 정지·방 변경이 있었으면 보내지 않는다 (cancelled)
  → 전송 허용 목록 확인 (~/.config/openkakao/config.toml [safety] allowed_send_chats)
  → 댓글 시도
       ├ 성공 (스레드에서 확인)                → via=thread
       ├ '전송'을 누르기 전에 막힘 (ThreadError) → 일반 메시지로 대신 보냄 → via=plain
       └ '전송'은 눌렀는데 확인 실패            → 다시 보내지 않음 → via=unverified
  → 보냈을 수 있는 문구는 SentLog 에 기억 (다음 폴링에서 질문으로 읽지 않게)
```

| 결과 | 뜻 | 봇의 처리 |
|---|---|---|
| `thread` | 댓글로 달림 | 정상 |
| `plain` | 댓글은 못 달고 일반 메시지로 보냄 (예: 방이 붐벼 질문이 화면 밖으로 밀림) | 정상, 사유는 audit `send_detail` |
| `unverified` | 나갔는지 모름 | **재전송 금지**, 운영자 알림, 오류로 셈 |
| `failed` | 보내지 못함 | 오류로 셈 (연속되면 서킷 브레이커) |
| `cancelled` | 보내기 직전 긴급 정지 등 | 오류 아님 |

- **허용 목록을 댓글 경로에서도 확인한다.** 일반 메시지는 openkakao-cli 가 막아 주지만 댓글은 AX 를
  직접 다뤄 CLI 를 거치지 않는다. 같은 파일을 읽어 두 경로가 한 목록을 따른다. 파일을 못 읽으면
  아무 데도 보내지 않는다.
- '전송' 버튼을 누른 뒤에는 `ThreadError` 를 내지 않는다 — 호출하는 쪽이 `ThreadError` 를 "아직 안
  보냈다"로 받아 대신 보내기 때문이다. 예상 못 한 예외도 "나갔는지 모름"으로 친다.
- ✅ **포커스를 뺏지 않는다** (2026-09-20 실측). 댓글 전송 3초 동안 맨 앞 앱과 커서를 30ms 간격으로
  기록했는데 한 번도 바뀌지 않았다 (맨 앞 앱 = Claude 유지). `AXShowMenu` 로 컨텍스트 메뉴를 열어도
  카카오톡이 앞으로 나오지 않는다.
- 본방에 올라간 사본은 `outgoing=True` 이고 본문이 보낸 문구와 **정확히 같다** ("Mina에게 댓글" 머리글은
  본문 밖의 별도 요소). 말풍선 위치와 SentLog 두 관문 모두에 걸린다.
- 같은 테스트에서 **답의 마크다운이 기호째 올라가는** 문제를 찾았다 (`- **1주차 종료 전**: 80% 환불`).
  카카오톡은 서식을 그리지 않는다. 시스템 프롬프트에 서식 금지 규칙(6)을 넣고, 보내기 전에
  `guard.to_chat_text()` 가 굵게·제목·코드 표시를 지우고 글머리표를 `· ` 로 바꾼다.


## 실전 테스트에서 드러난 제약 (2026-09-20)

질문 9개를 한꺼번에 올려놓고 봇에게 처리시키자 첫 답이 **일반 메시지로** 나갔다.
로그는 "컨텍스트 메뉴에 '댓글' 항목이 없습니다". 원인은 둘이었다.

### ① 화면 밖 메시지에는 메뉴가 열리지 않는다

`AXShowMenu` 가 **0(성공)을 돌려주고도 아무 일도 하지 않는다.** 보이는 영역 안에 있는
셀에만 메뉴가 뜬다. 봇이 답을 올리면 화면이 아래로 밀리므로 앞선 질문은 금세 밖으로 나간다.

    보이는 영역  y 450~882
    대상 메시지  y 410~447   ← 37px 위로 벗어남 → 메뉴 안 열림

**해결**: 메뉴를 열기 전에 세로 스크롤바의 `AXValue`(0~1)를 계산해 대상을 가운데로 가져온다.
셀에는 액션이 하나도 없어서(`AXScrollToVisible` 조차 없다) 스크롤바를 직접 움직이는 수밖에 없다.
전송 뒤에는 우리가 바꾼 값만 되돌린다 — 새 메시지로 카카오톡이 스스로 맨 아래로 내렸으면 그대로 둔다.

### ② 컨텍스트 메뉴는 앱이 아니라 **그 창** 아래에 붙는다

앱 전체를 훑으면 메인 목록 창(채팅 451개)까지 훑어 **12초 이상** 걸린다. 창 아래만 얕게(깊이 6)
보면 즉시 찾는다. 고정 대기(0.6초) 대신 메뉴가 뜰 때까지 최대 2.5초 기다린다.

> 운영 팁: 카카오톡 **메인 목록 창은 닫아 두는 편이 빠르다.** 봇은 방 창만 있으면 된다.

## 봇이 연 창만 쓰고 닫는다 (2026-09-24)

예전에는 '제목 없고 동시전송 체크박스가 있는 **첫** 창'을 스레드 창으로 잡고, 끝나면
`댓글 달린 메시지` 창을 **모두** 닫았다. 운영자가 스레드 창을 열어 두고 쓰는 중이면 그 창에
봇의 답을 쓰거나 그 창을 닫을 수 있었다.

지금은 '댓글'을 고르기 **전**의 스레드 창·부속 창 목록을 기억해 두고, **새로 생긴 창만**
쓰고 닫는다. 같은 스레드를 운영자가 이미 열어 두어 새 창이 안 생기면 손대지 않고 멈춘다
(`ThreadError` → 일반 메시지 대체 경로). AX 요소는 `==` 로 같은 창인지 비교된다 (CFEqual).

스레드 안의 추가 질문에 답할 때는 같은 본문의 원글 중 몇 번째인지(`nth`)와 그 스레드에 있어야
할 추가 질문(`expect`)을 넘긴다. 없으면 엉뚱한 스레드이므로 보내지 않는다 — `docs/followup.md`.
